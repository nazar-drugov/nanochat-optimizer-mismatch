# Project-specific agent instructions

These instructions record Harry Gong's working agreement with his agents for the
optimizer-mismatch study. Follow them alongside the applicable instructions of
the coding environment. This is a shared research branch with two collaborating
authors, not a single-agent project.

## Session startup and persistent memory

- At the beginning of **every session**, and again before beginning any
  substantive task, read `.codex/MEMORY.md` and consult its relevant contents.
  This repository-local memory is persistent and private; `.codex/` is gitignored.
- At session startup, also consult `HANDOFF.md`, and use
  `PRETRAINING_PROTOCOL.md`, `LOG_CHANGES.md`, and `reports/` to understand the
  current scientific and operational state. Do not assume an older status is
  current when either collaborator may have advanced the work.
- Keep memory current with Harry's durable preferences and working norms. Record
  shared scientific decisions, experimental protocols, and results in the
  appropriate tracked project documents, not only in private memory.

## Scientific intent and planning

- **Always ask Harry for his explicit scientific intent before running an
  experiment.** Do not guess the scientific objective or infer approval from a
  question about feasibility, an exploratory discussion, or a suggested plan.
  Establish what hypothesis or question the experiment addresses, what it should
  measure, and what outcome would answer that question.
- Before implementing a substantive change or experiment, thoroughly analyze its
  scientific merits and plan it carefully: hypotheses, controls, comparisons,
  assumptions, confounders, data and measurement choices, success criteria,
  compute requirements, and validation as relevant. Check against the existing
  protocol and the other collaborator's work.
- If there is ambiguity about intent, design, interpretation, or scope, ask Harry
  searching, specific questions and challenge assumptions constructively until
  the ambiguity is resolved. Do not silently choose an unagreed scientific
  design. Obtain agreement to the experiment plan before carrying it out.
- When a scientific question or request has multiple plausible interpretations,
  explicitly present the alternative ways to answer it, explain how their
  estimands, assumptions, controls, and implementation differ, and ask Harry
  which reflects his intent. Continue asking focused, substantive questions
  until confident the scientific intent and implementation details are settled;
  do not mistake a convenient interpretation for the intended one.

## Execute agreed plans to completion

- Once Harry has agreed to the plan, implement it fully, including the agreed
  checks, analysis, and reporting. Maintain a clear list of completed and
  outstanding work. When there is further work, explicitly say:
  "There is a lot more to do! Namely:" and enumerate the remaining plan items
  that have not yet been completed or verified; then continue doing them.
- Do not ask whether to continue an already approved plan or stop at an
  intermediate milestone that is not the agreed completion condition. Only seek
  further input if a scientifically material deviation, missing authorization,
  or genuine blocker requires it.
- When a bottleneck arises, diagnose it, try appropriate alternatives, and work
  toward the original scientific purpose. Preserve the controls and agreed
  assumptions; do not give up or silently replace the experiment with an easier
  but scientifically different one.

## Correctness before compute

- Write and run unit tests for **all substantive code changes**. Use an independent
  subagent to review and test those changes for correctness before committing
  compute to a cluster experiment. Resolve review findings and verify the fixes.
  Include regression tests for bugs and appropriate end-to-end checks where
  warranted. A job script regenerated by an already reviewed generator with only
  approved run parameters changed should be checked against a reviewed script.
- Never launch a new or changed training/analysis path on the cluster before
  the required correctness checks and subagent review pass. This does not require
  a new review of read-only inspection, documentation edits, or unchanged,
  previously reviewed code invoked with approved parameters.

## Weights & Biases experiment tracking

- Log **every experimental run** (pretraining, fine-tuning, LR sweeps, pilot
  length branches, main grids, ablations, and reruns) to W&B. Keep the project
  organized: stable descriptive run names, explicit stage/dataset/optimizer
  metadata, pretraining and fine-tuning seeds, LR, run length, and tags/groups
  separating sweeps, pilot, main, and extended runs. Distinguish failed and
  invalid runs from valid scientific evidence; never silently mix them.
- Verify logging is working before committing new compute, and verify that
  completed runs are present. If a run was executed without W&B, backfill it
  from the authoritative saved metrics rather than rerunning training merely
  for logging. Avoid duplicate tracking runs when requeueing or resuming.
- Keep the local experiment records authoritative and preserve them even if
  W&B is unavailable: log offline and sync later if needed; explicitly alert
  Harry to logging failures or missing credentials. Never print or commit API
  keys or upload raw training/evaluation documents or checkpoints just for
  tracking.

## Scientific reporting

- After **every scientifically significant milestone**, create a human-readable
  milestone-specific Markdown report in `reports/`. Keep it concise and informative:
  scientific question, agreed setup, key results, interpretation, limitations,
  and next open decisions, with links to supporting data or figures.
- Record decisions in `PRETRAINING_PROTOCOL.md`, implementation and run outcomes
  in `LOG_CHANGES.md`, and the current status in `HANDOFF.md` as appropriate.
  Distinguish confirmed results from exploratory or invalid runs. Respect the
  authors' commitment in `docs/report.tex` to author their own paper prose.
- Maintain the global cross-author checkpoint registry (`CHECKPOINTS.md` and
  `results/checkpoint_registry/`). Refresh the inventory after each significant
  run batch or path change; include both collaborators' actual checkpoint paths
  and clearly distinguish model weights, evaluation arrays, and invalid or
  verification-only runs. Never infer that a checkpoint exists from its name.
